# Forwarded-Student Portal Auth

**Jira**: https://concord-consortium.atlassian.net/browse/RIGSE-352
**Repo**: https://github.com/concord-consortium/rigse
**Implementation Spec**: [implementation.md](implementation.md)
**Status**: **In Development**

## Overview

When a student clicks an "I'm Done" button in a study activity, an automated report-service job calls back into the portal to move the student between classes, lock or unlock their activities, and notify their teacher. Today all of those calls run as one fixed high-privilege account, so the automated job can reach any student's data. This story makes each call act as the specific student who clicked, with only that student's access, while still requiring verified proof that the call came from the sanctioned service.

## Project Owner Overview

The "I'm Done" button lets students in a controlled research study self-serve their own randomization, activity gating, and teacher notification, without a teacher doing it by hand. In the spring 2026 pilot, every portal action the button triggered ran as a single shared administrator account wielded by an automated service. That does not scale to a multi-teacher fall study, and it concentrates a large amount of privilege in one credential: if that credential were leaked or misused, it could reach any student's or teacher's data across the portal.

This story makes each portal action attributable to, and scoped to, the actual student who clicked, so the automated flow follows least-privilege: a call can only ever touch the resources of the one student it names, and only when it also proves it came from the sanctioned service. It ships in two phases so existing spring behavior is preserved during the transition, with the high-privilege fallback removed only after the new path is verified in production. It is the first and blocking piece of the fall randomized-controlled-trial work spanning three repositories (portal, report-service, question-interactives).

## Background

This is story **R1** in the "I'm Done" button fall-RCT breakdown (epic **DT-20**), and the long pole on the critical path: report-service story **REPORT-83** (forward the student identity) is blocked on it, and the fall report-service stories (**REPORT-79/80/81/82**) depend on it transitively.

### How it works today (spring-2026 pilot)

report-service authenticates to the portal with a Google-issued OIDC ID token minted for the Cloud Function's runtime service account (`portalOidcFetch` in report-service). The portal's `OidcBearerTokenAuthenticatable::BearerToken` Devise strategy (`rails/lib/oidc_bearer_token_authenticatable.rb`) verifies that token against Google's JWKS (`GoogleOidcVerifier`), looks up `Admin::OidcClient.find_by(sub:)`, and calls `success!(oidc_client.user)`. So `current_user` becomes one fixed mapped portal user for every report-service action.

The three portal calls report-service makes:

| Call | Endpoint | Controller | Authorization today |
|---|---|---|---|
| Enroll / move student into a class | `POST /api/v1/students/add_to_class` | `API::V1::StudentsController#add_to_class` | `Portal::ClazzPolicy#update_roster?` (teacher/admin/project-admin) then `student :show?` |
| Lock / hide the student's offering | `PUT /api/v1/offerings/:id/update_student_metadata` | `API::V1::OfferingsController#update_student_metadata` | `Portal::OfferingPolicy#update?` (class teacher or global admin) |
| Notify the teacher | `POST /api/v1/emails/oidc_send` | `API::V1::EmailsController#oidc_send` | `API::V1::EmailPolicy#oidc_send?` (any OIDC-auth user; emails `current_user.email`) |

Because `update?` accepts only a class teacher or a global `admin` (project-admin is not enough), the single mapped user must in practice hold the global `admin` role to lock offerings across arbitrary classes. That single global-admin credential, wielded by a Cloud Function, is the over-privilege this story removes.

### The chosen model (design doc "model F", decision O3 refined 2026-07-21)

Every report-service portal call acts as the **verified student**, using two credentials that are **both required**:

1. **The existing OIDC service token** proves the request came from the trusted report-service caller. It no longer selects a user.
2. **The student's portal-minted Firebase JWT**, forwarded by report-service (REPORT-83) on each call, establishes who to act as. The portal already mints this token (`SignedJwt::create_firebase_token`, via `API::V1::JwtController#firebase`) and report-service already holds it on `StepContext.firebaseJwt` (it uses it today to read the student's own answers from Firestore).

The portal verifies the forwarded Firebase JWT and sets `current_user` to that student. Crucially, this is a **learner** JWT, and a `Portal::Learner` ties one student to one offering (and thus one class): it is minted for the student running the activity the button sits in. Decoding it (`API::V1::JwtController#firebase`, jwt_controller.rb:234-273) yields both the acting identity and the origin context:

- `platform_user_id` = `user.id`, so the portal resolves the exact portal user to act as (no hash-reversal problem; the Firebase `uid` itself is an MD5 hash and is not used for this).
- `offering_id` = the origin offering (the button's `resource_link_id`) and `class_hash` = that offering's class.

So the origin offering and origin class arrive as **verified token claims**, not as caller-supplied parameters. The per-operation checks below anchor to that origin rather than granting the full student identity free rein over all of the student's classes.

Neither token alone is sufficient. A student's Firebase JWT without the trusted-service OIDC token must never authorize these operations, or a student could call the portal directly and unlock content, move themselves between classes, or email their teacher at will. The service token marks the request as coming through the sanctioned report-service path; the student token scopes it to that one student.

Because there is exactly one `Admin::OidcClient` (one service-account `sub`, used solely by report-service's three callers), this is a **migration of one record**, not a new client: null out its mapped `user_id`, add a `requires_forwarded_jwt` flag, and add a capability declaring it may perform the forwarded-student lifecycle operations.

### One button for both programs (decision O14)

The PI wants a single Green pre-test with **one** authored "I'm Done" button serving **both** the Flex and Full-Time programs. A single authored button carries one set of `taskParams`, so the program (and therefore which report-service job runs, `fall-2026-fulltime` vs `fall-2026-flex`) can no longer be an authored `pilot=` param. Instead, report-service resolves the student's **origin class word** at runtime and classifies the program by prefix (`FT-` = full-time, `FL-` = flex).

This touches RIGSE-352 only lightly. Under model F report-service already acts as the student, so it reads the student's own origin offering and class from the portal (`offerings/:id` then `classes/:id`) to get the class word. Those reads are already permitted for the acting student (`api_show?` allows `class_student?`), so no new policy is needed; the only optional rigse change is exposing `class_word` on the offering serializer so the resolution is one call instead of two. The resolution logic and program dispatch live in report-service (REPORT-79/REPORT-82).

### Forwarded-student authentication

- The portal must accept, on report-service's portal calls, an additional forwarded student learner (Firebase) JWT alongside the existing OIDC service token, carried in the **`X-Portal-Student-JWT`** request header (raw token, no `Bearer` prefix) so it does not collide with the OIDC token in `Authorization`. This header name is the cross-repo contract with report-service (REPORT-83).
- When a valid forwarded student learner JWT is present on an OIDC-authenticated report-service request, the OIDC auth path must set `current_user` to the student named by that token (resolved from the token's `claims.platform_user_id`, an integer nested under the `claims` object), not to any mapped/admin user.
- The forwarded-student override must be **scoped to an opted-in OIDC client**, not applied to every OIDC client. The override (switching `current_user` from the mapped user to the forwarded student) must be honored **only** when the resolved `Admin::OidcClient` is configured for the forwarded-JWT path - operationalized as **`oidc_client.capabilities.present?`** (the client declares at least one lifecycle capability; a dedicated `allows_forwarded_jwt` opt-in flag is an acceptable alternative if the team prefers decoupling the opt-in from capabilities). This is required because the OIDC strategy is generic - it authenticates any active client by `sub` and calls `success!(oidc_client.user)` (oidc_bearer_token_authenticatable.rb:33-47), and the model/admin CRUD support multiple clients - so without an auth-time opt-in gate a forwarded header could silently switch **any** active client's identity to the student on **all** student-authorized endpoints (the operation capabilities gate the new lifecycle policy branches, but only *after* `current_user` is chosen, so they do not prevent the identity switch itself). Gating the override makes the OIDC-client-migration guarantee - "the existing record and any future client authenticate via the mapped user until Phase 2" - literally hold. For a **non-opted-in** client, the forwarded header is **ignored** and the client authenticates as its mapped user (existing behavior, unchanged by this story), so the fail-closed-on-present-header rule (below) applies **only to opted-in clients**; a present-but-invalid header on a non-opted-in client is not this story's concern (that client has no forwarded-student path). Phase 1 keeps working because the service client is granted its capabilities with the schema migration, so it is opted in from the first deploy (before the header-present override is relied on). (A `requires_forwarded_jwt=true` client should always also hold capabilities - the migration grants both - so it too is opted in.)
- The forwarded token must additionally be verified to be a **learner** token as a fail-closed auth rule, not merely by convention: `claims.user_type` must equal `"learner"` **and** the resolved user must have a `portal_student` (`User#portal_student` present). Otherwise the request fails closed with `forwarded_token_invalid`. This matters because `API::V1::JwtController#firebase` mints several custom-token shapes under the same nested `claims`, and `offering_id`/`class_hash` are **not** learner-exclusive (other branches set them too, jwt_controller.rb) - only the learner branch sets `user_type: "learner"` (jwt_controller.rb:267). Without this check an implementer could satisfy every enumerated check with a teacher/researcher token that happens to carry offering/class context and thereby act with a non-student identity; the per-operation policy checks (target `user_id == current_user.id`, `owner?`) already assume a student, so the auth layer must guarantee it. (Both-tokens-required already blocks a student calling directly; this closes the "wrong portal-minted token forwarded" gap as defense-in-depth.)
- Before trusting the token, the portal must confirm its `claims.platform_id` matches this portal's `APP_CONFIG[:site_url]`, so a learner token minted for a different portal cannot be replayed here.
- The origin offering and class must be resolved from the token's `claims.offering_id` as the **single canonical anchor**: the origin offering is the offering with id `claims.offering_id` and the origin class is that offering's `offering.clazz`. All three forwarded-token resolutions (user via `claims.platform_user_id`, origin offering via `claims.offering_id`, origin clazz via `offering.clazz`) must **fail closed as `401 forwarded_token_invalid`** when the record is missing or nil - they must **not** use a bang `find`/`find!` that would surface the API base controller's `RecordNotFound` handler as an **HTTP 404** (api_controller.rb:4,116-121), nor let a nil `offering.clazz` raise a `NoMethodError` → 500. Use `find_by` (or a rescued `find`) and route the not-found/nil case into the forwarded-invalid failure. The token's `claims.class_hash` is a **cross-check only**, never an independent resolution path: if `offering.clazz.class_hash != claims.class_hash` the request must fail closed with `forwarded_token_invalid`. (The two claims are minted from the same offering, jwt_controller.rb:268-269, so a mismatch signals a tampered or malformed token.) No operation resolves the origin class by a `class_hash` lookup (`Portal::Clazz.find_by_class_hash` exists but is deliberately not used here); `offering_id -> offering.clazz` is the one derivation used everywhere, for lock and enroll alike.
- The forwarded learner JWT must be verified (signature and expiry) using the portal's own Firebase signing key before it is trusted. Expiry is enforced with **zero clock-skew leeway** (no `exp_leeway`), which is intentional for this path: the portal both mints and re-verifies the token on its own clock, so there is no cross-vendor skew to absorb, and a genuinely expired token must fail closed (see the resolved async-expiry Open Question, which rejected widening skew/lifetime). Do not add an `exp_leeway`. The verifying `FirebaseApp` is resolved from the token's `iss` claim (which equals the app's `client_email`), and the signature is checked against that app's RSA key. This is a small addition to the `SignedJwt` verification path, which today only resolves an app by name. This resolution assumes `client_email` uniquely identifies a `FirebaseApp`; note that is not enforced today (only `name` is indexed, schema.rb:386, and `FirebaseApp` validates `client_email` format but not uniqueness, firebase_app.rb), so if the assumption ever stops holding, RSA-key selection stays deterministic by **verifying the signature against each `iss`-matched candidate app's RSA key and accepting the one whose key validates the token** (then applying the app-name allowlist check to that resolved app; a candidate that signs the token but is not allowlisted still fails closed as `forwarded_token_invalid`). This is stronger than a name-only disambiguation: only the app that actually signed the token is ever accepted.
- The resolved app must additionally be a member of a configured allowlist of app name(s) trusted for the forwarded-JWT path (defaulting to the report-service app, e.g. `report-service-pro` / `report-service-dev`), so a valid learner token minted for any other portal Firebase app cannot be honored on this lifecycle path. The allowlist is config-only; no `firebase_apps` schema or admin-form change.
- The origin context asserted by the token (`offering_id` and `class_hash`) must be made available to the authorization layer (for example via `request.env['portal.auth_details']` or a dedicated env key), so per-operation checks can anchor to the verified origin offering/class rather than to the student's full enrollment set.
- When the forwarded token is expired or otherwise invalid, the portal must fail closed and return a **distinguishable** error (separate from "OIDC service token invalid" and from an authorization denial), so report-service can surface a clear retry message to the student and the async failure is diagnosable in logs. The token has a hard ~1-hour life (nominal 3600s, effectively ~3570s after the 30s `iat` backdate - see the Token-lifetime Technical Note) and the portal cannot extend or re-mint it. The fail-closed rule is keyed on the header being **present**: a present-but-unverifiable forwarded token fails closed in both rollout phases and must never fall through to the legacy mapped user (see Two-phase rollout); only the total **absence** of the header engages the Phase 1 legacy fallback.
- The distinguishable-error contract (shared with REPORT-83) is the set of signals report-service branches on (three 401 `error_code`s plus the 403 authorization denial): **HTTP 401** with a stable `error_code: "forwarded_token_invalid"` (forwarded token present but fails any check: signature, expiry, `platform_id`, app allowlist, or any resolution of a token-asserted record - the acting user (`platform_user_id`), the origin offering (`offering_id`), or the origin clazz (`offering.clazz`) being missing/nil, or the `class_hash` cross-check mismatching; each such resolution must fail closed as this 401, never as a bare 404/500); **HTTP 401** with `error_code: "oidc_token_invalid"` (OIDC service token invalid / no matching client / inactive); **HTTP 401** with `error_code: "forwarded_token_required"` (**Phase 2 only**: the client's `requires_forwarded_jwt` is set but the `X-Portal-Student-JWT` header is **absent**, so there is no forwarded token to verify and, with `user_id` null, no mapped-user fallback - kept distinct from `forwarded_token_invalid` so report-service can tell "header not forwarded / stripped in transit" apart from "forwarded token present but bad"); and **HTTP 403** `{ success: false, message: "Not authorized" }` (capability or per-operation access denial, the existing Pundit path, unchanged). report-service distinguishes authentication (401) from authorization (403) by status, then the 401 kinds by `error_code`. The `error_code` field must be a **top-level** key in the JSON error body (`{ success: false, response_type: "ERROR", error_code: "...", message: "..." }`), because REPORT-83 branches on it: it must not be buried under `details` or any nested object. Note the existing `API::APIController#error(message, status, details)` (api_controller.rb:86-93) renders only `success`/`response_type`/`message`/optional `details` and has **no** `error_code` slot, so producing this response requires either extending `error` to accept and render a top-level `error_code:` or a dedicated auth-error render; grep confirms no `error_code` is emitted anywhere in the app today. Acceptance tests must assert the exact top-level JSON path for `forwarded_token_invalid`, `oidc_token_invalid`, and `forwarded_token_required`. How the Warden strategy surfaces the per-case code (distinct failure message symbol mapped to `error_code` by the API failure rendering / controller detection) is an `implementation.md` detail; the top-level placement is a contract requirement, not.
- The forwarded-invalid response must **fail closed as an authentication `401`** carrying `error_code: "forwarded_token_invalid"`, and must **not** degrade into the `403 { success:false, message:"Not authorized" }` authorization-denial signal (nor a generic `401` without `error_code`). This is a required observable outcome, called out because it is **not** the default behavior: these endpoints have no `authenticate_user!` filter and the strategy fails non-bang, so a failed strategy today simply nulls `current_user` and surfaces as a Pundit `403` (metadata/roster) or an `error_code`-less `401` (`oidc_send`) - see the "How auth failures actually render today" Technical Note. Implementation must actively fail closed. The mechanism is **not** a strategy-level `fail!`: under this app's lazy `current_user` (non-bang `warden.authenticate`, no `authenticate_user!` filter), a strategy's `fail!` only halts the strategy chain and nulls `current_user` - it does **not** invoke `CustomFailure`, which fires only from a bang `authenticate!` call site these endpoints do not have (verified against warden-1.2.9; see the "How auth failures actually render today" Technical Note). The realistic mechanism is therefore **controller-level detect-and-render** via `error(...)` (or introducing an explicit bang authentication / `throw(:warden)` call site); the exact choice is an `implementation.md` decision, but strategy `fail!` alone is insufficient. The 401-not-403 outcome is the binding requirement.
- The auth layer must continue to stamp request metadata identifying the auth strategy and client (`request.env['portal.auth_strategy']`, `portal.auth_client`, `portal.auth_details`) so policies can detect the trusted forwarded-student path.
- The rewritten OIDC strategy must declare `store? => false` (the Warden/Devise idiom for token strategies), so a successful `success!(current_user)` does not serialize the acting identity into a Rack session or emit a `Set-Cookie`. This is a correctness fix the rewrite must carry: the strategy has no `store?` override today (oidc_bearer_token_authenticatable.rb, verified), so under the forwarded-student override Warden would attempt to persist a **per-request student** into a session on every stateless report-service call. Token auth must stay sessionless; the acting identity lives only for the one request.
- The rewritten OIDC strategy must also suppress Devise `:trackable` on this path by setting `request.env['devise.skip_trackable'] = true` before `success!`. `store? => false` prevents only **session serialization**; it does **not** prevent the separate `after_set_user` trackable hook, which Warden's `set_user` runs regardless of `store:` (warden-1.2.9 proxy.rb:170 gates only the session write on `store:`, then always runs `after_set_user`). `User` is `:trackable` (user.rb:11, confirmed at runtime), and nothing in the app sets `devise.skip_trackable` today (grep of app/lib/config). Without this, an acting-as-student `success!` fires `update_tracked_fields!` on **every** report-service call, incrementing the real student's `sign_in_count` and overwriting `current/last_sign_in_at` and `current/last_sign_in_ip` (the latter with the Cloud Function's egress IP), then `save(validate: false)` (devise-4.9.4 models/trackable.rb) - a silent corruption of production sign-in-tracking data. Acting as the student must be stateless in tracking as well as in session. (Today's fixed-mapped-user `success!` already bumps one service account's tracking harmlessly; the override is what turns this into per-student corruption.)

### OIDC client migration

- The single `Admin::OidcClient` record must be migratable to have a null `user_id` (no mapped fallback user). Because `admin_oidc_clients.user_id` is currently `NOT NULL`, this requires a `change_column_null(:admin_oidc_clients, :user_id, true)` migration; there is no foreign-key constraint to drop (only a plain index on `user_id`). This **schema** change (nullable column) is Phase-1-safe and is separate from the Phase-2 **data** change that actually nulls the value (see the per-phase state table in Two-phase rollout). Reversibility caveat: `change_column_null(..., true)` is itself reversible, but once the Phase-2 data step has nulled `user_id`, a rollback that re-imposes `NOT NULL` will fail against the null row; a Phase-2 rollback must first re-populate `user_id` with the mapped user.
- The `Admin::OidcClient` model must gain a `requires_forwarded_jwt` flag, added as a DB column with **`default: false, null: false`** (mirroring the sibling `active` column's `default: true, null: false`, schema.rb), so Phase 1 is the default state and the existing record (and any future client) authenticates via the mapped user until Phase 2 explicitly flips it. When set, the client cannot authenticate without a valid forwarded student Firebase JWT; there is no fallback to a mapped user. (This "future clients default to mapped-user" guarantee is enforced at the strategy level by the opt-in gate in Forwarded-student authentication: a client with no lifecycle capabilities never honors the forwarded-student override, so a stray forwarded header cannot switch its identity.)
- The `validates :user, presence: true` model validation must be made **conditional** rather than removed outright: `user` must be present **unless `requires_forwarded_jwt` is true** (e.g. `validates :user, presence: true, unless: :requires_forwarded_jwt?`). Removing it entirely would permit the invalid state `requires_forwarded_jwt=false` + `user_id=nil` - a mapped-fallback client whose header-absent path cannot produce a mapped user. The conditional keeps the invariant that a legacy/fallback client (the Phase-1 state) still requires a mapped user, while allowing the null-user client only once it has been flipped to require the forwarded JWT (the Phase-2 state). No `belongs_to :user, optional: true` change is needed: the app sets `config.active_record.belongs_to_required_by_default = false` in every environment, so the bare `belongs_to :user` is already optional and presence is enforced solely by this explicit (now conditional) validation. Model specs must cover: `requires_forwarded_jwt=false` + null user **rejected**, `requires_forwarded_jwt=true` + null user **allowed**, `requires_forwarded_jwt=false` + user **allowed**.

#### Generic per-operation capabilities

- `admin_oidc_clients` must gain a **generic** `capabilities` set column (`serialize :capabilities, type: Array`, following the `Admin::Settings#enabled_bookmark_types` precedent). The schema carries no feature-specific column; a client holds a set of named operation capabilities.
- The recognized capabilities must be declared once, in a single registry constant `Admin::OidcClient::CAPABILITIES` (a frozen hash of `identifier => human-readable label`), which is the sole source of truth. For this story the registry contains three generic portal-operation identifiers (no "pipeline"/"im-done" naming):
  - `enroll_student` (guards `students#add_to_class`)
  - `update_offering_state` (guards `offerings#update_student_metadata`: lock / hide / open)
  - `send_teacher_email` (guards `emails#teacher_send`, delivered by RIGSE-353)
- `Admin::OidcClient#capability?(name)` must return whether the client's `capabilities` set includes `name.to_s`. It is a model-level predicate, unit-testable off the request path. It must treat an unset/`nil` `capabilities` as the **empty set** (return `false`, never raise): a `serialize :capabilities, type: Array` column has no value-level default, and the admin checkbox form omits the param when nothing is checked, so a client can persist with `capabilities == nil`. Guard it the way the `enabled_bookmark_types` precedent does (`self.enabled_bookmark_types ||= []`, settings.rb:34), e.g. normalize to `[]` in the getter/predicate.
- The model must validate that every stored capability is a key of `CAPABILITIES` (reject unknown/typo'd identifiers). This validation must also no-op cleanly on an unset/`nil` or empty set (nothing to reject).
- The admin CRUD form must render one checkbox per registered capability (iterating `CAPABILITIES`, using the label as help text), rather than a free-text field, and the controller's permitted params must accept the `capabilities` set.
- A capability grants permission to invoke that operation; it never elevates the acting identity to a teacher. It is a separate layer from the per-operation access checks below (capability = "may this client invoke this op at all"; access check = "and only on resources this forwarded student may touch"). Both are required.
- The migrated client is granted exactly the capabilities report-service uses (`enroll_student`, `update_offering_state`, `send_teacher_email`).

### Authorization (current_user is always the student)

- The trusted forwarded-student metadata branch must be added to a **new, action-scoped** policy query `Portal::OfferingPolicy#update_student_metadata?`, **not** to the shared `Portal::OfferingPolicy#update?`. This is a required scoping: `update?` also gates the class-wide `API::V1::OfferingsController#update` action (`authorize offering` → `update?` by Pundit action inference, offerings_controller.rb:29), which writes `active`/`locked` across **all** of the offering's `UserOfferingMetadata` rows (offerings_controller.rb:40-47) - a class-wide mutation. If the forwarded-student branch lived on `update?`, a forwarded-student call to `PUT /api/v1/offerings/:id` (route live at routes.rb:393) would be authorized for that class-wide lock/hide (strong params drop `user_id`, but authorization would already have passed). So: define `update_student_metadata?` to dispatch to the trusted forwarded-student branch **exclusively** when acting as the forwarded student and otherwise to `class_teacher_or_admin?` (`return forwarded_update_offering_state? if oidc_context.acting_as_forwarded_user?; class_teacher_or_admin?`), change the `update_student_metadata` controller action to `authorize offering, :update_student_metadata?`, and leave `offerings#update` on the bare `update?` (teacher/admin only, unchanged). The trusted forwarded-student branch allows the operation when: the resolved client holds the `update_offering_state` capability, `current_user` is a student, the target `user_id` is that same student, and that student has access to the target resource per the per-operation checks below. `current_user` must never be elevated to a teacher. The two branches are **mutually exclusive by auth path, not additive**: a forwarded-student request is bound to the student-scoped branch and never falls through to `class_teacher_or_admin?`. This is a required least-privilege property, because `current_user`'s portal roles are independent of the forwarded identity: a forwarded learner token minted for a user who is *also* a class teacher / global admin / project-admin would otherwise satisfy `class_teacher_or_admin?` and bypass every student-scoped guard (self-identity, origin, open-only). Non-forwarded teacher/admin requests still reach `class_teacher_or_admin?` and keep updating any student's metadata in their class without the self-identity restriction.
- The trusted forwarded-student enroll branch must likewise be added to a **new, action-scoped** policy query `Portal::ClazzPolicy#add_to_class?`, **not** to the shared `Portal::ClazzPolicy#update_roster?`. Required scoping: `update_roster?` also gates `API::V1::StudentsController#remove_from_class` (`authorize portal_clazz, :update_roster?`, students_controller.rb:215, route live at routes.rb:341), which then `destroy`s an arbitrary `Portal::StudentClazz` (students_controller.rb:217) with **no** `student :show?`/owner binding and **no** capability check. If the forwarded-student branch lived on `update_roster?`, a forwarded-student call could remove *any* student from a same-teacher class. So: define `add_to_class?` to dispatch to the trusted forwarded-student enroll branch **exclusively** when acting as the forwarded student (which requires the `enroll_student` capability) and otherwise to `update_roster?` (`return forwarded_enroll_student? if oidc_context.acting_as_forwarded_user?; update_roster?`), change the `add_to_class` controller action to `authorize portal_clazz, :add_to_class?`, and leave `remove_from_class` on the bare `update_roster?` (teacher/admin/project-admin only, unchanged). The two branches are **mutually exclusive by auth path**, for the same least-privilege reason as `update_student_metadata?`: a forwarded token minted for a user who is independently a teacher/admin must not reach `update_roster?`. The follow-on `authorize student, :show?` check in `add_to_class` is retained as defense-in-depth but is **no longer the load-bearing identity guard**, because `Portal::StudentPolicy#show?` also passes via `admin?`, teacher-of-record, or project-admin: for a forwarded token whose user independently holds one of those roles, `show?` would not deny enrolling a *different* student. So the forwarded enroll branch must itself bind the target to the acting student: `forwarded_enroll_student?` requires **every** provided identifier (`user_id` and/or `student_id`) to resolve to the acting student, in addition to the shared-teacher class constraint. It must be *every* provided identifier, not *any*, because `find_student_from_params` (students_controller.rb:272) prioritizes `student_id` over `user_id`: an any-match check would let a token for student A send `user_id=<A>` (satisfying the check) plus `student_id=<B>` and have the controller enroll B, defeating the "enroll only adds the acting student themselves" guarantee.
- Each policy branch must check the capability that names its own operation (`enroll_student` for enroll, `update_offering_state` for lock/hide/open, `send_teacher_email` for the RIGSE-353 email path), not a single lumped capability.
- Detection of the trusted path must resolve the client by a **stable identifier**, not by `portal.auth_client`: the strategy stamps `portal.auth_client = oidc_client.name` today (oidc_bearer_token_authenticatable.rb:45), and `name` has **no** uniqueness validation (only `sub` is unique, oidc_client.rb) - so a name lookup can resolve the wrong client if two clients share a display name. The rewritten strategy must instead stamp a stable key (e.g. `portal.auth_client_id`, or the client record itself for request-local use) and resolution must key on that; `portal.auth_client` (name) stays as display/logging metadata only. Trusted-path detection otherwise follows the precedent of `API::V1::EmailPolicy#oidc_send?` (which authorizes on the auth strategy plus a truthy `user`: `user && request.env['portal.auth_strategy'] == 'oidc_bearer_token'`), and must go through the shared helpers below, not inline `request.env` reads. (This is the same stamping the reusable-helpers requirement calls for - "stamp enough on `request.env` ... to resolve the client record"; the two requirements are consistent: resolve by id, never by name.)

### Reusable auth helpers (shared with RIGSE-353)

- This story must deliver reusable Rails helpers so that detecting the trusted OIDC path and checking client capabilities is a one-liner for callers, rather than each policy or controller re-implementing the `request.env['portal.auth_*']` lookups and capability logic inline. RIGSE-353's `teacher_send` authorization must be able to reuse these helpers unchanged.
- The request-scoped logic must live in a single generic PORO, `OidcAuthContext` (in `lib/`), constructed from a request (or an env hash, for testability). It must expose at minimum:
  - `#client` -> the acting `Admin::OidcClient` for the request, or nil when the request did not come in through the OIDC strategy.
  - `#acting_as_forwarded_user?` -> whether a forwarded-student override is in effect (`current_user` is the forwarded student rather than a mapped user).
  - `#origin_offering_id` / `#origin_class_hash` -> the raw origin claims asserted by the forwarded learner token, and `#origin_offering` / `#origin_clazz` -> the **resolved** `Portal::Offering` / `Portal::Clazz`, so lock and enroll anchor to the **same** resolved object rather than each re-deriving from a raw claim. These resolutions must **not** use a bang `find` (which would surface the API base controller's `RecordNotFound` handler as a 404, api_controller.rb:4,116-121): the origin offering/clazz are either already resolved and validated by the forwarded-token verifier (preferred, so the fail-closed check happens once at auth time) or resolved here via `find_by`/rescued lookup, with a missing offering or nil `offering.clazz` routed to `401 error_code:"forwarded_token_invalid"` (see the Forwarded-student authentication requirement), never a bare 404/500. The `class_hash` claim is used only to cross-check `origin_clazz.class_hash` (fail closed on mismatch), never as an independent `find_by_class_hash` lookup.
  - `#capability?(name)` -> delegates to `client&.capability?(name)` (the model predicate).
- The `OidcAuthContext` PORO (constructible from a request **or** an env hash) is the canonical shared surface: any caller that has a request/env can build it. `ApplicationPolicy` must gain a thin memoized accessor (e.g. `oidc_context` returning `OidcAuthContext.new(request)`) as a **convenience for policies in that hierarchy**, so R1's `Portal::OfferingPolicy#update_student_metadata?` and `Portal::ClazzPolicy#add_to_class?` (both `ApplicationPolicy` subclasses) express their trusted-path branch identically. Controllers use the PORO directly.
- The existing `API::V1::EmailPolicy` is a plain `Struct` (not an `ApplicationPolicy` subclass), so it would not inherit the `oidc_context` accessor. RIGSE-352 does **not** refactor it. RIGSE-353's `teacher_send` authorization may therefore either extend `ApplicationPolicy` (to use the accessor) or construct `OidcAuthContext` directly from its request (as a Struct policy would); RIGSE-352 guarantees both paths by giving the PORO a request-or-env constructor. The "all three policies consume the same accessor" framing is thus scoped to the PORO as the shared contract, with the `ApplicationPolicy` accessor being convenience-only.
- The pure capability predicate stays on the model (`Admin::OidcClient#capability?`, see the registry above), unit-testable off the request path; `OidcAuthContext` layers the request context on top.
- The rewritten OIDC strategy must stamp enough on `request.env` for `OidcAuthContext` to resolve the client record (e.g. the client id) and to expose the forwarded-token origin claims, rather than only the client name it stamps today.

### Per-operation access checks

These checks apply **only within the forwarded-student branch** of `Portal::OfferingPolicy#update_student_metadata?` (the new action-scoped query; see the Authorization requirement). The teacher/admin path is unchanged: it still passes via the existing `class_teacher_or_admin?` clause, and a teacher may set metadata for any student in their class (no self-identity restriction). The controller's existing guard that the target `user_id` is a student in the target offering's class (`offering.clazz.students.find_by(user_id:)`, offerings_controller.rb:57) runs for everyone and stays as-is; the self-identity condition below is added only in the forwarded-student branch, never as a blanket endpoint rule (which would wrongly break teachers).

- **Lock or hide the current offering** (`update_student_metadata`, `locked`/`active`; capability `update_offering_state`): allowed when the target offering is the token's asserted origin `offering_id` **and** the target `user_id` equals the acting student (`current_user.id`).
- **Open a target offering** (`update_student_metadata`, unlock + make visible; capability `update_offering_state`): the target offering is a different offering than the origin (Blue/Orange). Allowed when the target `user_id` equals the acting student (`current_user.id`) **and** the target offering belongs to a class the student is enrolled in (the controller's student-in-class guard already enforces the latter) **and** the written values are open-only. The target-user condition is required here just as for lock; without it a call acting as student A could flip another student B's metadata in the same class. The scope is intentionally the acting student's own enrollment: the target-user guard confines the blast radius to that one student's own view/lock state.
  - **Value constraint (v1 requirement, promoted from "optional" per a 2026-07-21 external-review round):** because `update_student_metadata` has no operation verb and simply writes whatever `active`/`locked` booleans are permitted (offerings_controller.rb:53-64, strong params permit only `:active, :locked` at :211-213), a branch that authorizes a non-origin offering by identity would otherwise also authorize `locked: true` / `active: false` on it. So for a **non-origin** target offering the forwarded-student branch must **deny** any write that sets `locked: true` or `active: false` (i.e. only unlock/`locked:false` and/or make-visible/`active:true` are permitted off-origin); `locked`/`hide` writes stay limited to the **origin** offering. This keeps "open" able only to open, so a capability-holding call cannot lock or hide the student's unrelated enrolled offerings. The policy branch has `params` access to enforce this; note `@params` is unset in some test contexts, so guard with `present?`.
    - **Boolean normalization (required):** the check must **cast** `params[:locked]` / `params[:active]` before comparing, not compare against a single literal representation. `update_student_metadata` passes the permitted params straight to ActiveRecord (offerings_controller.rb:63-64), and Rails' boolean coercion treats `true`/`"true"`/`"1"`/`1` as true and `false`/`"false"`/`"0"`/`0` as false, so a request can send the off-origin `locked` as the string `"true"` (or a JSON boolean `true`) - a policy that compares only to `true` (or only to `"true"`) would miss the other form and let the write through. Normalize with `ActiveModel::Type::Boolean.new.cast(params[:locked])` (and `...cast(params[:active])`) and enforce the open-only rule on the cast value. Add tests covering both string (`"true"`/`"false"`) and JSON-boolean (`true`/`false`) inputs for the off-origin deny.
- **Enroll into a class** (`add_to_class`; capability `enroll_student`): the outlier, because the student is not yet in the target class, so ownership does not apply. The origin class is `origin_clazz`, resolved from `claims.offering_id` via `offering.clazz` (the same single anchor used for lock; the `class_hash` claim is only the fail-closed cross-check, not a `find_by_class_hash` lookup). Allowed when the target class shares at least one teacher with that origin class (`(origin_clazz.teachers & target_clazz.teachers).any?`, comparing against **any** teacher of the origin class, not just the primary), and the target class is not archived (`Portal::Clazz#is_archived`, a schema-backed boolean defaulting `false`, portal_clazzes schema).
  - **Accepted residual risk (documented inline per a 2026-07-21 external-review round):** this rule admits **any** non-archived class taught by any origin co-teacher, which is broader than "a sanctioned study subclass" - a report-service bug or a bad target-class-word resolution could enroll the student into an unrelated same-teacher class. This breadth is **accepted**, not an oversight, for three reasons: (a) enroll only ever adds the **acting student themselves** (bound by `forwarded_enroll_student?`'s `target_is_acting_student?`, which requires every provided `user_id`/`student_id` to resolve to the acting student and so denies enrolling anyone else; `Portal::StudentPolicy#show?` is retained only as defense-in-depth and is no longer relied on for this, since its admin/teacher/project-admin clauses would pass for a privileged acting-user), so no third party is exposed; (b) the target class is one the **origin teacher already fully controls** (they can add any student to their own class roster directly), so it stays inside that teacher's existing trust domain; and (c) the narrower alternatives were considered and rejected in the enroll Open Question - a class-word suffix / report-service-supplied prefix cross-checked by the portal pushes a report-service/authoring naming convention into a portal policy (wrong layer, brittle to renames), and a project/cohort/program marker needs project wiring the study does not require (a reasonable **future** broadening, not v1). If a future study needs a tighter boundary, option C (same-project/cohort) is the intended next step. See the RESOLVED enroll Open Question for the full options analysis.
- **Reading the student's own answers** already runs as the student via the forwarded token and is enforced by Firestore data-security rules. No portal change.
- **Resolve the origin class word** (reads; no state change; no capability required; decision O14): to classify the student's program, report-service (acting as the student) reads its own origin offering and class, `GET /api/v1/offerings/:id` (`resource_link_id`) for `clazz_id`, then `GET /api/v1/classes/:id` for `class_word`. These need **no new policy branch**: `Portal::OfferingPolicy#api_show?` and `Portal::ClazzPolicy#api_show?` already allow `class_student?`, so the acting student is authorized, and no lifecycle capability applies to reads. Recorded here as part of the sanctioned forwarded-student surface under the act-as-student path.

### Origin-class-word resolution convenience (O14)

- **(Optional optimization, not a completion blocker.)** Optionally add `class_word` (sourced from `offering.clazz.class_word`) to the `API::V1::Offering` show serializer, alongside the existing `clazz` / `clazz_hash` / `clazz_id` attributes, so report-service can resolve the origin class word from the single `offerings/:id` read rather than a second `classes/:id` call. This is a pure optimization: the two-call fallback already works because `classes#show` exposes `class_word` today (classes_controller.rb:138) and the acting student is authorized for both reads, so RIGSE-352 is **complete without this field**. It is the only rigse code change O14 would involve, and it is optional (report-service can make the second call instead). If delivered, add a serializer test asserting `class_word` is present; if not, no acceptance item depends on it. (Consistent with the Overview, which calls this the "only optional rigse change.")

### Two-phase rollout

- **Phase 1**: the auth layer accepts either credential path, but the fallback is gated on the **absence** of the `X-Portal-Student-JWT` header, not on "no *valid* token." If the header is absent, fall back to the legacy mapped user (the spring report-service path). If the header is present, the forwarded token must verify: on any failure (signature, expiry, `platform_id`, app allowlist, acting-user resolution, origin-offering resolution, nil origin clazz, or `class_hash` cross-check mismatch - the full line-73 list) the request fails closed with the distinguishable error and **never** falls back to the mapped user. This holds in both phases, so a present-but-unverifiable student token can never escalate to the mapped (admin) credential. This ships alongside report-service forwarding the token (REPORT-83) and is verified in staging and production against the live spring report-service flow.
- A present-but-invalid forwarded token (header supplied, verification failed) must be logged/metriced distinctly from both the header-absent fallback and a successful override, since it is the earliest signal that the ~1-hour token (effectively ~3570s) is expiring in-flight (or of a replay attempt). This logging must record the **fact and failure reason** (e.g. expiry vs signature vs `platform_id` vs allowlist vs resolution), never the raw forwarded JWT itself: it is a live bearer credential valid for the student's own session, so emitting it into logs would leak an act-as-student token. (The existing OIDC strategy already sanitizes what it logs - it logs only the issuer via `sanitize_log`, oidc_bearer_token_authenticatable.rb:24,55-58 - so this follows precedent.)
- The **header-absent-but-OIDC-present** fallback must itself be logged/metriced in Phase 1 (an OIDC-authenticated report-service call that fell back to the mapped user because `X-Portal-Student-JWT` was missing). Once report-service (REPORT-83) is forwarding the header on every report-service call, this rate should trend to zero; a non-trivial or rising rate is the tripwire that an intermediary is silently stripping the `X-Portal-Student-JWT` header (a custom header deliberately kept **off** the `X-Forwarded-*` namespace to reduce this risk - see the header-name Open Question caveat), which fails **open** to the mapped admin rather than closed. This is the only observable that distinguishes "report-service not yet forwarding" from "a proxy ate the header," and it is cheap to emit from the same fallback branch.
- **Cross-repo sequencing (notify step must migrate before the override goes live)**: the forwarded-student override is global across the **opted-in** client's endpoints (it applies to *every* call from that opted-in service client that carries a valid forwarded header - see the opt-in gate in Forwarded-student authentication), not per-endpoint. The legacy notify call `emails#oidc_send` emails `current_user.email` (emails_controller.rb:19,27,37), so under the override it would email the **student**, not the teacher. Therefore report-service must switch the notify step to `teacher_send` (RIGSE-353) - or not forward the header on the notify call - **before/when** it begins forwarding the header on report-service's other portal calls. If the override is enabled while notify still calls `oidc_send` with the header forwarded, teacher notifications silently misroute to students. RIGSE-352 does not change `oidc_send`; this is a rollout-ordering obligation the override creates, recorded here so the three-repo rollout sequences it correctly.
- **Phase 2**: the client is flipped to `requires_forwarded_jwt = true` with `user_id = null`, removing the legacy mapped-user fallback for good. A header-absent call to this now-flipped client (valid OIDC token, no `X-Portal-Student-JWT`) must fail closed as **`401` + top-level `error_code: "forwarded_token_required"`** (never a bare 401/403 and never a mapped user), so report-service can distinguish "the header stopped being forwarded / was stripped" from a present-but-bad forwarded token.

**Per-phase data state of the one `Admin::OidcClient` record.** The override is active as soon as the code ships (Phase 1), so the client must already hold its `capabilities` in Phase 1 for a header-present call to authorize; but `user_id` must stay set and `requires_forwarded_jwt` must stay `false` in Phase 1 so a header-**absent** call still falls back to the mapped user (spring preserved). The two data states are therefore distinct, and only the schema/capability changes ship with the code deploy:

| Field | Phase 1 (code deployed; report-service forwarding the header) | Phase 2 (fallback removed) |
|---|---|---|
| `user_id` | mapped user (unchanged) | `null` |
| `requires_forwarded_jwt` | `false` (column default) | `true` |
| `capabilities` | `[enroll_student, update_offering_state, send_teacher_email]` | same |

So the **schema migration** (nullable `user_id`, new `capabilities` + `requires_forwarded_jwt` columns with safe defaults, relaxed `validates :user`) plus the **capability grant** on the record ship together and are Phase-1-safe. The `user_id -> null` and `requires_forwarded_jwt -> true` flip is a **separate Phase-2 data step** (rake task / console / a later data migration), gated on report-service forwarding the header in production and on the notify step having moved off `oidc_send` (see the cross-repo sequencing bullet). Combining the Phase-2 data flip into the same migration as the schema change would enact Phase 2 at deploy and break the Phase-1 fallback.

### Acceptance criteria (from the ticket)

- Report-service portal calls act as the student; after phase 2 no action runs as the legacy mapped user.
- After phase 2 the service client cannot authenticate without a valid forwarded student Firebase JWT.
- A student cannot perform these lifecycle operations by calling the portal directly without report-service's service token.
- Existing production (spring) report-service behavior is preserved through the migration.

### Acceptance test scenarios

Concrete cases that operationalize the acceptance criteria across the two-phase rollout. Each names its natural spec home; detailed test code lives in implementation.md.

**Acts-as-student / both-tokens-required** (`spec/controllers/api/v1/oidc_auth_spec.rb`, `spec/libs/bearer_token/oidc_bearer_token_authenticatable_spec.rb`):
- Phase 1, `X-Portal-Student-JWT` absent: OIDC token only acts as the mapped user (`success!(oidc_client.user)`) - spring behavior preserved.
- OIDC token + valid forwarded learner JWT: `current_user` is the forwarded student; origin `offering_id`/`class_hash` and client id are stamped on `request.env`.
- OIDC token + valid forwarded learner JWT: the acting-as-student path suppresses Devise `:trackable` so the real student's tracking fields (`sign_in_count`, `current/last_sign_in_at`, `current/last_sign_in_ip`) are not overwritten by the report-service call. This is asserted at the **mechanism level** (`request.env['devise.skip_trackable'] == true` is set on the forwarded path before `success!`), **not** by comparing tracking-field values before/after the call: the field-level outcome rests on Devise's own verified handling of `devise.skip_trackable` (devise-4.9.4 `hooks/trackable.rb`, which skips `update_tracked_fields!` when the flag is set - independently confirmed against the pinned gem), and the full Warden `set_user` / `after_set_user` chain is not reliably reproducible in specs (see the implementation.md testing note). A field-level assertion is intentionally not required.
- OIDC token + forwarded JWT present but invalid (expired / bad signature / wrong `platform_id` / app not in allowlist / user unresolvable / origin `offering_id` points to a missing offering / origin clazz nil / `class_hash` cross-check mismatch): `401` + `error_code:"forwarded_token_invalid"` (specifically **not** a 404 or 500), and it **never** falls back to the mapped user (assert in both phases).
- **Invalid OIDC service token (the second 401 signal)**: each of the strategy's three OIDC failure paths (oidc_bearer_token_authenticatable.rb:31-50) - Google verification failure, no matching `Admin::OidcClient` for the `sub`, and inactive client - must surface at the **request level** as `401` with top-level `error_code:"oidc_token_invalid"`, with no fall-through to forwarded-student or mapped-user behavior. (This is the half of the cross-repo branching contract the existing specs, which assert only strategy-level failure or a generic "must be logged in" error, do not yet cover.)
- Forwarded JWT present but **no** OIDC service token: rejected (a student cannot invoke these operations directly - AC3). **This is verified at the request/controller level (see Request-level below), not here**: with no `Authorization` header the OIDC strategy is never selected, so `current_user` stays nil and the denial is a controller/Pundit behavior a strategy unit test cannot exercise.
- Phase 2 (`requires_forwarded_jwt = true`, `user_id` null), header absent: cannot authenticate; asserts `401` with top-level `error_code:"forwarded_token_required"` (the exact JSON path), no mapped-user fallback, and distinct from the `forwarded_token_invalid` and `oidc_token_invalid` bodies.
- `platform_id` mismatch (token minted for a different portal): `forwarded_token_invalid` (replay defense).
- Non-learner forwarded token (a validly-signed portal Firebase custom token whose `claims.user_type` is teacher/researcher/absent, or whose resolved user has no `portal_student`): rejected with `forwarded_token_invalid`, never acted upon.
- **Opt-in gate**: an active OIDC client with **no** lifecycle capabilities (not opted in) that receives a valid forwarded learner JWT header authenticates as its **mapped user** - the override is not honored and the forwarded header is ignored (no identity switch). The opted-in service client (capabilities present) with the same header acts as the student. (Guards the "future clients default to mapped-user" guarantee.)
- `exp` 1 second in the past: rejected (zero clock-skew leeway on Firebase decode).

**Capability + migration** (`spec/models/admin/oidc_client_spec.rb`):
- `capability?(name)` returns true/false per the stored `capabilities` set.
- Validation rejects a capability identifier that is not a key of `CAPABILITIES`.
- Conditional user-presence validation: a client with `requires_forwarded_jwt=false` and a null `user` is **rejected**; one with `requires_forwarded_jwt=true` and a null `user` is **allowed** (the Phase-2 state); one with `requires_forwarded_jwt=false` and a `user` is **allowed** (the Phase-1 state).
- The one record's **Phase-1** state after the schema migration + capability grant: `user_id` still set (mapped user), `requires_forwarded_jwt = false` (column default), `capabilities = [enroll_student, update_offering_state, send_teacher_email]` (so the header-present override authorizes while the header-absent path still falls back). The separate **Phase-2** data step then flips it to null `user_id`, `requires_forwarded_jwt = true`, capabilities unchanged. Test both states (see the per-phase state table in Two-phase rollout); the migration itself must not produce the Phase-2 state.

**Authorization** (`spec/policies/portal/offering_policy_spec.rb`, the clazz policy spec):
- `OfferingPolicy#update_student_metadata?` forwarded-student branch (and a scoping test that the class-wide `update?`/`offerings#update` path does **not** get the forwarded-student branch, and that a forwarded token whose user is *also* a class teacher/admin is still bound to student-scope): lock of the origin offering for the acting student with `update_offering_state` **allowed**; **denied** without the capability; **denied** when target `user_id` != acting student; teacher/admin path still allowed unchanged; open (`locked:false`/`active:true`) of a non-origin offering in an enrolled class **allowed**; open of an offering in a class the student is not in **denied**; a **`locked:true` or `active:false` write to a non-origin offering denied** (the v1 open-only value constraint), while the same write to the **origin** offering is allowed (lock/hide).
- `ClazzPolicy#add_to_class?` forwarded-student branch: enroll **allowed** with `enroll_student` when the target class shares any teacher with the origin class (including a **co-teacher**) and the target class is not archived; **denied** on no shared teacher; **denied** on an archived target class. Plus a scoping test that `remove_from_class` (bare `update_roster?`) does **not** get the forwarded-student branch (a forwarded-student call to `remove_from_class` is denied), and that a forwarded token whose user is *also* a teacher/admin cannot enroll a different student (mismatched `user_id`, mismatched `student_id`, **and the mixed `user_id=<self>` + `student_id=<other>` case**, all denied in the forwarded branch itself; the consistent both-present-and-self case allowed).

**Request-level** (`spec/controllers/api/v1/{offerings,students}_controller_spec.rb`):
- `add_to_class`: forwarded-student enroll happy path; enrolling a **different** student than the acting one is denied in the forwarded enroll branch itself (`target_is_acting_student?`), not merely via `student :show?` / `owner?`. Cover mismatched `user_id`, mismatched `student_id`, and the **mixed `user_id=<self>` + `student_id=<other>`** case (denied even though `user_id` matches, because the controller enrolls the `student_id`).
- `update_student_metadata`: lock-origin happy path; open-target happy path; acting-as-A modifying B's metadata is denied.
- **Direct-call denial (AC3)**: a request with the `X-Portal-Student-JWT` header present but **no** OIDC `Authorization` header is rejected (Pundit 403, `current_user` nil) and mutates nothing - assert for both `update_student_metadata` (no `UserOfferingMetadata` upsert) and `add_to_class` (no `StudentClazz` created). This is the request-level home of the "forwarded JWT without the OIDC token" scenario above, since the strategy is never invoked without an `Authorization` header.

## Technical Notes

- **OIDC strategy**: `rails/lib/oidc_bearer_token_authenticatable.rb`. Today: verify Google token, `find_by(sub:)`, stamp `portal.auth_*`, `success!(oidc_client.user)` (line 47). The forwarded-JWT handling and the student resolution slot in here. **Session/`store?`**: the strategy has **no `store?` override** today (verified full-file read), so `success!` runs Warden's default serialization; the rewrite must add `store? => false` so acting-as-student never persists to a session (see the Forwarded-student authentication requirement). `valid?` (lines 6-26) peeks the unverified issuer to decide whether this strategy claims the `Authorization` header, and `oidc_token_value` (lines 60-69) explicitly declines `Bearer/JWT` so the `JwtBearerTokenAuthenticatable` strategy keeps that scheme; the forwarded header (`X-Portal-Student-JWT`) does not participate in this routing.
- **Devise `:trackable` on the acting-as-student path (verified: runtime + pinned gem source)**: `User` enables `:trackable` (user.rb:11; `User.devise_modules.include?(:trackable) == true` confirmed in the app container). Warden's `set_user` runs the `after_set_user` callbacks even when `store: false` - `store:` gates only `session_serializer.store`, not the callbacks (warden-1.2.9 lib/warden/proxy.rb:170). The OIDC strategy fails with **non-bang** `fail(:invalid_token)` (oidc_bearer_token_authenticatable.rb:36,50), so a failed strategy leaves `current_user == nil` and Warden's failure app (`CustomFailure`, a `Devise::FailureApp`, wired at devise.rb:278) is **never reached** on this path (it only fires on **bang** authenticate). With `current_user` nil, an invalid token today renders as a **Pundit 403** `{success:false, message:"Not authorized"}` on `update_student_metadata`/`add_to_class` (identical to the authz-denial signal) and as a **generic 401 without `error_code`** on `oidc_send` (via `require_api_user!`, api_controller.rb:96-99). **Verified against warden-1.2.9 (proxy.rb:109 non-bang `authenticate`, proxy.rb:132 bang `authenticate!`, strategies/base.rb:137 `fail!`, base.rb:145 `fail`):** a strategy's `fail!` is **not** equivalent to a bang `authenticate!`. `fail!` only `halt!`s the strategy and marks it failed; the `throw(:warden)` that reaches `CustomFailure` happens **only** inside `Proxy#authenticate!` (bang) at the call site. Since these endpoints authenticate lazily via `current_user` → `Proxy#authenticate` (non-bang) with no `authenticate_user!` filter, a strategy `fail!` returns a `nil` user and `CustomFailure` is **never reached** - the only observable difference from `fail` is whether *later strategies* run. Producing the distinguishable **401 + `error_code`** therefore requires one of: **(recommended) controller-level detect-and-render** via `error(...)` (verify the forwarded token in the action or a shared helper and render the JSON error body directly); or introducing an explicit bang `authenticate!` / `throw(:warden)` call site **and** teaching `CustomFailure` to render the API JSON error body (which it does not do today - it does `http_auth`/redirect, custom_failure.rb). The exact mechanism is an `implementation.md` decision; the observable outcome (401 + `error_code`, never the 403 authz signal, never fall-through to the mapped user) is a requirement (see Forwarded-student authentication). (This corrects the second-pass entry's claim that a strategy `fail!` "then routes to `CustomFailure`"; see the fourth-pass Self-Review.)

### RESOLVED: What is the exact "sanctioned destination class" rule for enroll?
**Context**: Enroll (`add_to_class`) is the one operation where the student is not yet a member of the target class, so the "student owns the resource" check that guards lock/hide/open cannot apply. The ticket explicitly states this rule "must be defined in this story." The **origin class is derived from the verified `claims.offering_id` via `offering.clazz`** (the single canonical anchor; `claims.class_hash` is only a fail-closed cross-check of `origin_clazz.class_hash`, never an independent `find_by_class_hash` lookup - see the resolved Decision below and the Forwarded-student authentication requirement), so the rule anchors to that resolved origin class. There is no class-to-class model relationship (no parent/section/subclass), and `class_word` has no enforced format, so the `-Gator`/`-Shark` suffix is a report-service/authoring convention that the portal cannot see. report-service resolves the target class word to a `clazz_id` at runtime via `classes/info`; the portal's job is only to enforce a trust boundary.
**Options considered**:
- A) **Origin-anchored shared-teacher rule**: allow only when the target class shares at least one teacher with the token's asserted origin class. Operationalizes "a sanctioned subclass of their origin class" as "a class taught by their origin class's teacher." Portal-verifiable, convention-agnostic, matches the study (Trudi teaches origin + Gator + Shark). Pair with a guard that the target class is not archived.
- B) **Class-word suffix rule**: allow only when the target class word is a sanctioned suffix (`-Gator`/`-Shark`) of the origin class word. Rejected: pushes a naming convention owned by report-service/authoring into a portal policy (wrong layer), brittle to renames, duplicates report-service's resolution work.
- C) **Same-project rule**: allow when the target class is in the same project as the origin class. Broader than shared-teacher (any project teacher's class qualifies) and needs project wiring the study does not require; a reasonable future broadening.

**Decision**: **A**, comparing against **any** teacher of the origin class (not just the primary `clazz.teacher`), since co-teachers of the origin class are equally trusted. The target class must also not be archived. The origin class is resolved from the token's verified `offering_id` claim via `offering.clazz` (with `class_hash` as a fail-closed cross-check, not an independent lookup), so no naming convention is encoded in the portal. (Resolution-method note added in the 2026-07-21 third self-review pass, which pinned `offering_id -> offering.clazz` as the single origin-class anchor.)

### RESOLVED: How is the capability modeled on the client, and how granular is it?
**Context**: The story calls for a capability declaring the client may perform the lifecycle operations. ### RESOLVED: Where do the shared OIDC/capability helpers live, and what is their surface?

- A) **Generic PORO wrapping the request** (`OidcAuthContext` in `lib/`) exposing `client` / `acting_as_forwarded_user?` / origin claims / `capability?(:op)`, plus a thin memoized `ApplicationPolicy#oidc_context` accessor. ### RESOLVED: In what header does report-service forward the student learner JWT?
**Context**: The `Authorization: Bearer` header carries the OIDC service token, so the forwarded student learner JWT needs a separate transport. The name is a contract shared with REPORT-83. It must not collide with the `Bearer`/`Bearer/JWT` routing that `JwtBearerTokenAuthenticatable` and `OidcBearerTokenAuthenticatable` use to claim the `Authorization` header. No existing forwarded-identity header convention exists in either repo.
**Options considered**:
- A) `X-Forwarded-Firebase-JWT`, raw token value: precise and self-documenting about the value the portal verifies (`decode_firebase_token`).
- B) A token-tech-neutral name (`X-Forwarded-User-Token`): more durable to a future token-tech change, less self-documenting.
- C) `X-Forwarded-Authorization: Bearer <token>`: mirrors a reverse-proxy convention; unnecessary scheme ceremony for a two-party internal contract.

**Decision (updated 2026-07-22)**: **`X-Portal-Student-JWT`** carrying the raw JWT (no `Bearer` prefix). This supersedes the original choice of `X-Forwarded-Firebase-JWT` (option A): the header is deliberately moved **off** the `X-Forwarded-*` namespace to eliminate the proxy-stripping / fail-open-to-admin exposure described in the caveat below (reverse proxies / CDNs / load balancers most commonly rewrite, normalize, or strip `X-Forwarded-*` headers). The custom `X-Portal-Student-JWT` name is still unambiguous, self-documenting (a portal-minted student token), non-`Bearer`, and trivially non-colliding with `Authorization`. This is a **cross-repo contract change that report-service (REPORT-83) must match** before either side forwards or reads the header. (Options B/C above remain the alternatives that were considered and rejected.)

**Caveat (proxy-stripping / fail-open surface, added 2026-07-21 third self-review pass; mitigated by the 2026-07-22 rename)**: the Phase-1 fallback is keyed on header **absence**, so any intermediary that silently drops the forwarded header does **not** fail closed - it downgrades the call to the legacy mapped user, which must hold global `admin` (`OfferingPolicy#update? = class_teacher_or_admin?`, offering_policy.rb:84), a silent privilege escalation rather than a denial. The original `X-Forwarded-Firebase-JWT` name sat in the `X-Forwarded-*` namespace that reverse proxies / CDNs / load balancers most commonly rewrite, normalize, or strip, which maximized this exposure. **Mitigation taken**: the header was renamed to the custom **`X-Portal-Student-JWT`** (off the `X-Forwarded-*` namespace), so a generic `X-Forwarded-*` normalization rule no longer touches it. Residual risk remains (an intermediary could still strip an unknown custom header, and evidence is limited because no reverse-proxy config lives in this repo - the portal's fronting infra is external, so this was a design caution, not a verified live strip), so the observability requirement in Two-phase rollout is retained: alert on a rising OIDC-present / header-absent rate in Phase 1 as the tripwire for a proxy silently eating the header. The rename is a cross-repo contract change REPORT-83 must match.

### RESOLVED: How does the portal know which FirebaseApp key to verify the forwarded token against?
**Context**: The token was minted for a specific `firebase_app`, and `SignedJwt::decode_firebase_token` today takes an app **name**. The portal must select the right RSA key when it receives the forwarded token. Empirically verified (2026-07-21): the token's `iss` equals the app's `client_email` (e.g. `report-service-pro@appspot.gserviceaccount.com`), which already exists on `firebase_apps` and is set via the admin form, so deriving the app from `iss` needs no schema or form change.
**Options considered**:
- A) Derive the app from the token's `iss`/`client_email`, verify the signature against that app's key. No extra param, robust across the two per-env apps; the OIDC service token stays the trust gate. Optionally pin to a config allowlist for defense-in-depth.
- B) A single configured app name for the path: simple, but hardcodes one app and needs per-env config; fails if the app changes.
- C) report-service forwards the app name (allowlist-checked): extra cross-repo coupling for no benefit over A.

**Decision**: **A with a config allowlist.** Resolve the `FirebaseApp` from the token's `iss` (= `client_email`) and verify the signature against that app's RSA key (a small addition to `SignedJwt`, which today resolves an app only by name). Additionally require the resolved app to be in a config-only allowlist of app name(s) trusted for the forwarded-JWT path (default: the report-service app), so a valid learner token from any other portal Firebase app cannot be honored here. Harmless for the two per-env report-service apps (distinct emails), but recorded as a stated assumption; if it ever breaks, disambiguate by verifying the signature against each `iss`-matched candidate's RSA key and accepting the one that validates, then allowlist-checking that app (see the Forwarded-student authentication requirement).

### RESOLVED: Is forwarded-JWT expiry a risk given the async report-service flow, and does this story need to address it?
**Context**: The forwarded custom token has a hard ~1-hour life (nominal 3600s, effectively ~3570s after the 30s `iat` backdate - see the Token-lifetime Technical Note; empirically confirmed) and is baked into the Cloud Task body at enqueue. The portal cannot extend or re-mint it (only the portal mints learner tokens, for the student's own session), and report-service's `executeTask` swallows step failures without rethrowing, so a portal 401 does not redeliver. A long-open activity, a backed-up serial queue, or an infra redelivery could present an expired token.
**Options considered**:
- A) Fail closed, define nothing extra: minimal, but the failure is indistinguishable from any other 401.
- B) Fail closed with a distinguishable error, so report-service can message the student and ops can diagnose; record the timing assumption as a cross-repo (REPORT-83) concern.
- C) Widen skew/lifetime for this path: rejected (weakens the credential and cannot fix a genuinely old token).

**Decision**: **B**. The portal fails closed and returns a distinguishable "forwarded token expired/invalid" error (separate from OIDC-token-invalid and from authorization denial). The cross-repo timing assumption (report-service must call the portal within the token's life; report-service bounds retry windows and cannot re-mint) is recorded in Technical Notes and is a REPORT-83 responsibility.
